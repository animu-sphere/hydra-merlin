# v0.10.0 - MaterialX shader-generation boundary

**Release date:** 2026-07-27
**Tag:** `v0.10.0`

## Objective

v0.10.0 establishes a durable, optional material-function boundary built on the
official MaterialX Slang Shader Generator. It is deliberately not a production
MaterialX support claim: it proves that a small, fully diagnosed graph slice and
the minimum Standard Surface subset can cross the host-neutral `MaterialIR`
boundary, execute in Vulkan Forward, and compile for SPIR-V and Metal without
giving MaterialX any ownership of the render pass.

The authoritative ownership, ABI, cache, diagnostic, and fallback rules are in
the [MaterialXGenSlang material boundary](../design/materialxgenslang-boundary.md).

## Completed capabilities

- Optional `Merlin::MaterialX` package and install target wrapping the pinned
  MaterialXGenSlang generator. No MaterialX SDK type appears in its public API,
  and MaterialX is not added to Core.
- Deterministic graph-only `evaluateMaterial` generation for constants and
  colors, image, texcoord/UV0, world normal, add, multiply, mix, and the minimum
  Standard Surface `base`, `base_color`, `metalness`, `specular_roughness`, and
  `normal` slice. Out-of-scope Standard Surface inputs are diagnosed explicitly
  rather than silently dropped.
- A versioned, host-neutral generated-material contract in Core covering module
  identity and revision, typed parameter state, logical texture/sampler
  bindings, and exact object/world/UV0 input requirements, with no MaterialX or
  backend-native types.
- One host-neutral shader module identity and target-artifact key in Core that
  key MaterialX-generated and handwritten Slang identically. Module identity
  covers source and include content, recovered from the compiler's own depfile;
  the separate artifact key adds compiler, target, profile, capability, layout,
  optimization, debug, target-option, ABI, permutation, and feature policy.
- `shaders/v2` artifact packages record module sources, module identity, and
  artifact key per artifact, and a test recomputes every recorded identity
  through the Core contract so the build system cannot drift from it.
- `merlin.material-abi/v1` in Core answers both halves of the agreement: whether
  a module satisfies what a consumer declares it can supply and will read, and
  whether a compiled artifact's reflected interface still describes the module
  it was built from. Agreement is semantic rather than positional, so SPIR-V and
  Metal describe one material through their own native bindings and agree with
  each other by agreeing with the module. The same contract owns the
  pass-neutrality rule, which `Merlin::MaterialX` applies to its own output.
- `merlin.material-diagnostic/v1` in Core owns the required-document,
  unsupported-node/input/conversion, missing library/include/texture,
  generation, compile, target, reflection, ABI, and cache failure categories,
  the context each record carries, the simplification, basic-material, and
  error-material fallback ladder, and an evidence aggregate reporting the worst
  fallback reached. A `Merlin::MaterialX` bridge flattens those records onto
  `merlin-diagnostic/v1`, so a host keeps one diagnostic stream while evidence
  consumers keep the structure.
- Vulkan Forward executes registered generated-material artifacts for both
  parameter-only and texture/sampler modules through per-module backend-owned
  descriptor and pipeline layouts. The backend verifies the Core consumer ABI
  and target reflection, packs typed instance values into target-specific
  uniform offsets, and reuses the module pipeline across value-only and
  texture-content edits. Lighting, depth, picking, AOV writes, and the render
  pass remain renderer-owned.
- Runtime generated-material capability, draw, fallback, and worst-rung
  telemetry on the Vulkan-native and backend-neutral result contracts, consumed
  by benchmark, headless renderer-report, native viewport benchmark, and Hydra
  regression serialization.
- Accepted prototype and Standard Surface Slang, SPIR-V, Metal-target, and
  reflection artifacts are retained and installed beneath `shaders/v2/materialx`;
  install-consumer validation requires the complete evidence set.

## Compatibility

- Core public APIs remain independent of MaterialX, OpenUSD, Hydra, Vulkan,
  GLFW, Qt, and DCC SDK types. The MaterialX integration exposes no Vulkan
  types, native handles, descriptor bindings, or pipeline layout.
- `MERLIN_ENABLE_MATERIALX=OFF` retains the existing Core and Vulkan build,
  tests, basic material path, and install contract. The MaterialX layer is
  optional and off by default.
- Vulkan 1.4 remains the minimum renderer contract. Conventional Forward remains
  the correctness and capability fallback, and the basic material path is
  unchanged.
- OpenUSD 26.05 remains the validated Hydra SDK/runtime boundary.
- Shader packages moved from `shaders/v1` to `shaders/v2`. Each artifact records
  `module_sources` and `module_identity` in place of `dependency_sha256`, and
  `artifact_key` in place of `cache_key`.
- The Forward shader ABI is version 3: conventional material constants moved to
  descriptor binding 31, reserving bindings 1 through 30 for generated material
  resources.
- `MaterialFunctionModule::cache_key` is removed. A compiled artifact's identity
  is now a distinct key built by `merlin::MakeShaderArtifactKey`.
- This release does not add a Metal renderer or presentation path, Gaussian
  shaders, GPU-driven submission, Visibility, or meshlets.

## Known limitations

- The supported graph slice is the accepted prototype plus the minimum Standard
  Surface subset. Arbitrary MaterialX documents and complete Standard Surface
  coverage are not claimed; unsupported constructs take a diagnosed fallback
  rung rather than rendering approximately.
- Hydra MaterialX ingestion is not part of this release. Hydra material
  translation remains the basic `UsdPreviewSurface`/`UsdUVTexture` subset.
- Full tangent-space normal mapping, production IBL, opacity/alpha mask and
  emissive coverage, asynchronous compilation, prewarming, and cache
  persistence/recovery remain v0.18.0 quality work.
- Metal remains a compile-and-reflection target rather than a renderer or
  presentation backend; the Metal-target evidence proves ABI agreement, not
  execution.
- `ost build` cannot enable `MERLIN_ENABLE_MATERIALX`, so the MaterialX layer is
  verified through a directly configured build rather than the OpenStrata
  managed path.
- Complete OpenChess Set fidelity is explicitly not claimed.

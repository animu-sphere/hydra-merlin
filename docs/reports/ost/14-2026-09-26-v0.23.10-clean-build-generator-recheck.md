# OST v0.23.10 clean-build generator recheck

- Date: 2026-09-26 (Asia/Tokyo)
- OpenStrata version exercised: `ost 0.23.10`
- Repository: `animu-sphere/hydra-merlin`
- Base revision: `f0ba589` (with uncommitted clang-format and README changes)
- Default OST target/profile: `cy2026` / `core`
- Host: Windows x86_64, MSVC 19.51 (Visual Studio 18), NVIDIA RTX A5000

This local follow-up to [report 13](13-2026-09-26-v0.23.8-recheck-v0.24.0-asks.md)
checks whether an install-consumer failure after a repository-wide formatting
pass survives a clean managed build. The prior managed Ninja build compiled,
but `ost test --jobs 4` passed only 37 of 38 CTests: `merlin-install-consumer`
failed in a nested CMake/Ninja compiler-ABI try-compile. An isolated rerun of
that test failed the same way.

## Clean-build observations

Before each clean configure, the existing managed core build directory was
moved aside under an ignored, dated sibling name; no source files or generated
builds were deleted. `ost build --check` had passed on this host.

| Fresh build | Result |
| --- | --- |
| Default Ninja generator, CMake 4.4.3 and Ninja 1.12.1 | Configure failed during CXX compiler ABI detection. Ninja `-t recompact` could not load `CMakeFiles\rules.ninja` from the try-compile tree. |
| Ninja generator, Visual Studio CMake 4.3.1-msvc1 and Ninja 1.13.2 | Same compiler-ABI try-compile failure on a separate fresh tree. |
| `Visual Studio 18 2026` generator, host `VULKAN_SDK` pointing to 1.3.290 | Compiler ABI detection passed, then project configure rejected Vulkan 1.3 because hdMerlin requires Vulkan 1.4 or newer. |
| `Visual Studio 18 2026` generator, Vulkan SDK 1.4.350 selected before a fresh configure | Build and output verification passed in 1m13s; `ost test --jobs 4` passed 38/38, including `merlin-install-consumer`. `ost validate --json` returned `ok: true`: configured, built, tested, renderer evidence, and core renderer assertions passed. |

The successful run used a session-local SDK override and no Ninja generator:

```powershell
$env:VULKAN_SDK = '<vulkan-sdk-1.4>'
$env:PATH = "$env:VULKAN_SDK/Bin;$env:PATH"
ost build --generator 'Visual Studio 18 2026' --jobs 4
ost test --jobs 4
ost validate --json
```

The SDK change alone is insufficient if a failed configure already cached the
1.3 SDK paths; the successful run used a new build directory. Report 13 also
records this host SDK selection and CMake cache behavior.

## Interpretation and limits

- The nested install-consumer failure was not a C++ compile regression from
  formatting: the fresh Visual Studio generator built and passed every CTest.
- Both tested CMake/Ninja pairs failed while reading a generated try-compile
  include. This establishes a local generator/toolchain failure, not which
  component wrote the problematic path. A standalone CMake reproduction without
  OST was not run, so this report does not assign an upstream owner.
- The final core validation passed, including `renderer.install_tree` after
  tests. Optional Hydra host, viewport launch, and packaging evidence were not
  exercised by this core run and remain explained skips.
- This is one Windows workstation and one core profile. No CI or other host was
  used to reproduce the Ninja failure in this pass.

The next diagnostic, if the Ninja route must be restored, is a minimal clean
CMake/Ninja try-compile on the same host with its generated `build.ninja` and
`rules.ninja` retained. No change to OST's default generator is proposed from
this single-host observation.

# Support matrix

**Last reviewed:** 2026-10-04

This matrix separates a required contract from a configuration actually
exercised by project CI or local capability validation. An unlisted platform may
work, but is not currently claimed as supported evidence.

## Toolchain and platform coverage

| Platform | Core | Vulkan/headless | Vulkan viewport | Hydra 2 | Evidence level |
| --- | --- | --- | --- | --- | --- |
| Windows x64, Visual Studio 2022 | Debug/Release | Debug/Release with Vulkan 1.4 | Debug/Release with GLFW; Release with Hydra USD loading | Release with OpenUSD 26.05 and 26.08 | Core hosted CI plus local Vulkan/MaterialX, native viewport, Hydra host-presentation, and Gaussian corpus validation; capability workflow retains the hardware evidence |
| Linux x64, hosted runner with Ninja | Debug/Release | Not continuously exercised | Not continuously exercised | Not continuously exercised | Core hosted CI |
| macOS 14, Apple Silicon, AppleClang 16 | Debug/Release | Native Metal offscreen Debug/Release; Vulkan not claimed | Native Metal `CAMetalLayer` viewport; Vulkan not claimed | Release with OpenUSD 26.08 and Metal | Hosted compile/package coverage plus local Apple GPU runtime AOV/residency, native presentation, and Kitchen Set Hydra validation |

A repository-scoped Windows x64 GPU runner is enrolled with the `vulkan-1.4`
label. The manual capability workflow exercises Vulkan Debug/Release and Hydra
Release on demand; it is capability evidence rather than a per-commit required
check.

The hosted workflow also defines GPU-free MaterialX generation and installed
consumer checks on Windows 2022 and Ubuntu 24.04, in Debug and Release. This
Tier 1 configuration explicitly disables `slangc` target artifacts; it checks
graph generation, the Core material ABI/diagnostics, and package linking.
All four configurations passed in [Core CI run 36710851814](https://github.com/animu-sphere/hydra-merlin/actions/runs/36710851814)
on 2026-09-30. This evidence does not expand the Vulkan, Metal-target, or Hydra
runtime claims above.

## Dependency contract

| Dependency | Minimum or validated version | Required by |
| --- | --- | --- |

| GLFW | 3.4; pinned commit fallback recorded in release metadata | `merlin-viewport` window/input plus Vulkan and Cocoa/Metal presentation adapters |

| OpenUSD | 26.05 and 26.08 currently validated | Hydra 2 only |
| MaterialX | 1.39.6 prototype pin at `38368ee04da84ce1f8837ecba7322dd6d81291f8`; source builds require CMake 3.26+ | Optional `Merlin::MaterialX` compiler |
| Metal | macOS system framework; Xcode Metal offline compiler and Slang 2026.8.x required to build; Metal argument-buffer tier 2 negotiated at runtime | Optional `Merlin::Metal` backend |
| Python + `testusdview` | Matching the OpenUSD runtime | Install-tree Hydra host test |

Hydra configuration verifies an accepted OpenUSD header version and the shared
library target layout. On MSVC it rejects a Debug hdMerlin build when the SDK
does not export Debug libraries. Plugin discovery and the install-tree usdview
test then load the runtime from that SDK root. Compiler/toolset ABI differences
between separately produced OpenUSD SDKs remain the operator's responsibility.

| Material ABI agreement | `merlin.material-abi/v1` is available in Core. A consumer declares the result fields it reads and the geometry inputs it can build, and a module is checked against that rather than in isolation. A compiled artifact's reflected interface is checked back against the module's logical one by name, type, and array size, so SPIR-V and Metal describe one material through their own native bindings and agree with each other by agreeing with the module. The same contract owns the pass-neutrality rule, which `Merlin::MaterialX` applies to its own output; both generated modules and all four of their SPIR-V/Metal artifacts are checked in the test suite, including the dropped, retyped, and undeclared-parameter cases |

| Metal Gaussian rendering | Available: shared CPU reference and opt-in GPU projection/covariance/SH, compaction, frame-wide radix sort, gather and indirect ellipse raster. Renderer-owned immutable attributes and completion-safe scratch avoid CPU particle traversal, sorting and prepared-stream uploads on GPU camera frames. Partial edits, source/handle identity, in-flight frames, resize, opaque Mesh composition, RGBA8 (2 channel units), exact depth/IDs, budget fallback and installed execution have local Apple GPU tests. SortedStream and Tiled support `prefer` and `require` on the tested Apple M3; unsupported tile allocation selects GPU SortedStream in `prefer` and reports Unsupported in `require`. Pair overflow keeps the complete sorted draw on the GPU. Resource/address limits fall back to CPU in `prefer` and report errors in `require`. Per-resource telemetry is read after completion; Metal statistics expose separate residency/scratch live bytes and dispatch/device-copy counts. CPU Disabled mode remains the default/reference. Synthetic 64K/1M local captures show camera/edit improvements but static GPU recomputation can cost more than CPU cached streams. Local 5.8M-particle SH-degree-3 Garden display was checked in the native viewport and usdview/HgiMetal GPU copy, including preferred tiled fallback; Hydra environment variables and viewport CLI options expose the pool budgets. Controlled Apple M3 HgiMetal comparisons cover the public 8,192-particle corpus and deterministic 1M scene, static/camera images, per-sample upload checks and device stage timestamps where supported. The 1M GPU sorted path removes the 52 MB moving-frame prepared upload but its roughly 100 ms raster remains the main device cost. Native tiled offscreen images pass 65K/1M Apple M3 comparisons with at most 2/255 RGBA8 difference and exact depth/IDs; a forced overflow matches the sorted image exactly. The tile raster stage is cheaper at both tested sizes, but total GPU time regresses because tile work outweighs that saving. An 8,192-particle HgiMetal GPU-copy tile capture selected compute raster and passed the host image policy, with a sparse 15/255 color tail; larger host captures and broader hardware performance claims remain open. Earlier CPU raster was checked with the 5.8M-particle stage in native viewport and usdview/HgiMetal; the Slang CPU path was manually checked in HgiMetal. |

Runtime comparison evidence covers image parity and no color Map/upload or coarse wait through resize. Merlin-owned Vulkan remains 1.4. Direct sharing reports `public-texture-import-unavailable` because public Hgi cannot import a Merlin-owned `VkImage`, so GPU copy remains selected. |

| GPU-driven indexed Mesh submission | Opt-in Vulkan execution: the backend-neutral CPU oracle validates persistent candidates, visibility/frustum culling, stable compaction identity, arena-block-safe indirect command batches, and exact counters. Renderer settings v2 exposes disabled, preferred-with-fallback, and required selection plus culling controls. The Vulkan runtime retains candidates per frame context, uses frame-shared buffers across arena/pipeline batches, compacts device-local indirect commands, and executes indirect-count draws. Metal rejects required selection and reports preferred fallback. Local RTX A5000 1k/10k/100k static/motion evidence covers basic and textured materials with 2/4/8/16 vertex arena blocks, zero preparation draw visits/uploads and exact four-AOV Forward parity; recording grows with batch count. | Standard OpenUSD Gaussian ingestion and rendering | Available on Vulkan: OpenUSD 26.05/26.08 `ParticleField3DGaussianSplat` through Hydra `particleField`, deterministic CPU preparation and sorting, procedural ellipse rasterization, mixed Mesh composition, IDs/picking, generation-checked persistent device-local position/covariance/opacity/SH ranges, zero-work static reuse, and range-only edits. Opt-in GPU preparation, frame-wide radix sorting, and sorted-stream indirect raster produce the image without a CPU-prepared upload and match the CPU-sorted reference image. Opt-in GPU tile binning produces verified per-tile pair ranges with bounded overflow, and opt-in compute tile raster composites them front to back with early termination, matching the CPU-sorted reference's depth and primId exactly and its color within a few rounding steps; an overflowing frame keeps the sorted-stream draws on the device. GPU-sorted frames skip the CPU preparation and sort unless validation against the CPU reference is requested; the CPU-sorted raster path remains the reference and fallback. Hosts select GPU execution through renderer settings v3 `gpu_driven_gaussian`; Hydra hosts such as usdview use the `merlin:gpuDrivenGaussian:enabled` and `merlin:gpuDrivenGaussian:tiled` flag render settings, or the unlisted `merlin:gpuDrivenGaussian:mode` and `merlin:gpuDrivenGaussian:raster` names. Separate GPU preparation/sort/tile/raster timestamps and warmed static/motion 1M/5M/10M comparisons are available. Local RTX A5000 captures have exact sorted-stream four-AOV parity at all tiers. After the v0.16.0 quality fix, Vulkan CPU/GPU sorted-stream and tiled execution use an RGBA32F working attachment and one final RGBA8 conversion, with pixel-center ellipse evaluation. Current RTX A5000 1M/5M/10M static/motion captures pass the unchanged six-step tiled color bound; the prior 10M 8/10-step failing captures are retained as historical evidence. Float blend/blit support is negotiated and reported by `gaussian_float_color_frame_count`; tiled additionally requires float storage-image support, with required rejection/preferred sorted-stream fallback when unavailable. Gaussian reference images remove legacy per-splat quantization error. Depth/primId remain exact; depth-tied instanceId differences stay within the established 1% allowance. These local timings have unpinned clocks/power and are not universal gates. |
